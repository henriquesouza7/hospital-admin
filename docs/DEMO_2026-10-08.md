## Acesso e autenticação

Não há URL de aplicação publicada neste corte. Para execução local, siga o
procedimento de `README.md` e `docs/NEON_SETUP.md`, usando um `.env.local`
ignorado pelo Git e valores obtidos por canal seguro no Neon. Nenhum arquivo de
ambiente original foi alterado.

usuário administrativo provisionado. A sessão existente de `localhost:3000`

- Nenhuma migration ou escrita ocorreu em `production`.

## Backup e restauração

1. Antes de uma migration ou mudança administrativa relevante, crie um snapshot
   manual da branch demo e registre a branch de origem, horário e nome do
   snapshot fora de arquivos com credenciais.
2. Restaure o snapshot como uma branch nova e temporária. Não informe uma branch
   de produção ou branch existente como destino.
3. Compare o schema restaurado com a origem e confira contagens e chaves de
   registros sintéticos de referência antes de apontar a aplicação para ela.
4. Em caso de falha, mantenha a origem intacta e use a branch restaurada como
   candidata de recuperação somente após validar aplicação, RLS e dados.
5. Não apague branches existentes. Considere limites e retenção do plano Neon
   antes de criar snapshots ou branches adicionais.

Teste executado em 08/10/2026: snapshot manual `hospital-demo-backup-20261008`
foi restaurado sem sobrescrever `production`. Um marcador sintético gravado
depois do snapshot permaneceu na branch de teste e estava ausente na branch
restaurada; o schema teve diff vazio e 20 tabelas públicas com RLS habilitada.
O projeto recusou um segundo snapshot por limite do recurso. A API Neon
renomeou branches durante a restauração direcionada; por isso, as próximas
restaurações devem criar uma branch nova sem informar destino existente e
confirmar o branch default antes de retomar a demonstração.
